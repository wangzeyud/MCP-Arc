# v0.5 技术方案：对齐 MCP 2026-07-28（Streamable HTTP + 方法无关透传）

> 目标版本：MCP 规范 **2026-07-28**。
> 范围红线：仅传输层；不新增"四件套"（脱敏/审计/回放/限流）之外的功能。
> 关联规则：`.codebuddy/rules/architecture/RULE.mdc`（红线第 1 条已改为 stdio + Streamable HTTP、方法无关透传）。

## 1. 关键规范事实（决定设计）

- **Streamable HTTP = 单 POST 端点**：请求/响应在同一 HTTP 交换内完成；响应可为 `application/json` 或 `text/event-stream`（按"请求作用域"的 SSE 流）。**无会话、无 `Last-Event-ID`、无 GET 发现端点**（GET→405）。
- **必须透传的头部**：`MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name`、`Mcp-Param-*`、`Origin`、`Accept`。SSE 响应须带 `X-Accel-Buffering: no` 且**立即分块、不缓冲**。
- **关闭流 = 取消信号**（双向传播）。
- **MRTR / `InputRequiredResult`**：server 在*同一原始请求*的响应里返回 `InputRequiredResult`（内含 `inputRequests: sampling/createMessage`），client 重试原请求并附 `inputResponses`。关联靠"响应包络属于原请求"，**无独立 sampling id**。`sampling` 在 2026-07-28 已 **deprecated**（SEP-2577），`elicitation` 是继任者、机制相同。

## 2. 现有架构落点

- 传输抽象：`transport.ClientTransporter` / `UpstreamTransporter`（`internal/transport/transport.go`），当前实现 `SSEServer`/`StdioClient`/`SSEUpstream`/`StdioUpstream`。
- 工厂在 `internal/proxy/proxy.go:127-154`：按 `transport.client/upstream`（目前 `sse`/`stdio`）选型。
- 拦截链：`processClientMessage`（`internal/proxy/interceptor.go:69`）解码 → 无 id 则透传、有 id 改写 `gw-N` 关联；`processUpstreamMessage`（`internal/proxy/interceptor.go:128`）无 id 则 `clientBroadcast`（`interceptor.go:133-137`）。

## 3. 核心设计决策

- **D1 客户端统一用 SSE 回包**：对 Streamable HTTP 客户端请求，始终以 `text/event-stream` 回包（每个 `respond` 调用 = 一个 SSE `data:` 事件）。理由：client 的 `Accept` 已含 `text/event-stream`，单响应的 SSE 流在规范下合法；这**规避了"必须先知道上游 content-type 才能写响应头"的 lookahead 难题**，且保持 `respond([]byte)` 逐帧契约不变。
- **D2 通知作用域（最关键改动）**：当前 `processUpstreamMessage` 把"无 id"一律当全局广播（`interceptor.go:133-137`）。但在 Streamable HTTP 下，`subscriptions/listen` 等长流响应里**没有 id 的通知是属于那个请求的**，不能广播给所有客户端。`StreamableHTTPUpstream` 适配器要记录"当前流所属请求 id"，把这些流内通知路由到对应 `pending.respond`，而非 `clientBroadcast`。stdio/SSE 行为保持不变。
- **D3 头部透传**：`StreamableHTTPUpstream` 在 client→upstream 复制 `MCP-*`/`Origin`/`Accept`；upstream→client 镜像响应头（去逐跳头）。
- **D4 取消传播**：`respond` 返回错误（client 断连）时触发该 `pending` 的取消钩子，中断上游流——实现"关闭流=取消"。
- **D5 通知 POST → 202**：无 id 请求转发后，transport 直接回 `202 Accepted`。
- **D6 向后兼容**：新增 Streamable HTTP；保留 stdio 与现有 SSE 适配器（标记 legacy，不动逻辑），避免破坏现有部署。

## 5. 风险与开放问题

- **T4 通知作用域是最大改动点**，必须小心不破坏现有 SSE 广播语义。
- `sampling` 已 deprecated → 是否还为其做脱敏？建议：**只审计不强制脱敏**，等 `elicitation` 稳定。
- 统一 SSE 回包是否会被极严格的 client 拒绝？规范允许，但需 soak 验证（T7）。
